# Curl 

## GET /posts/1: 200 OK
 
- Метод GET: Запрашивает чтение данных с сервера без изменения их состояния.
- Путь /posts/1: Указывает на обращение к первому элементу в списке постов.
- Код 200 OK: Стандартный HTTP-статус, сообщающий, что запрос принят, обработан и в теле ответа переданы запрошенные данные 

## GET /posts/999999: 404 Not Found

- Метод GET: Клиент запрашивает чтение данных с сервера без их изменения.
- Путь /posts/999999: Указание на коллекцию posts и конкретную запись с ID 999999.
- Статус 404 Not Found: Сервер подтверждает, что маршрут настроен правильно, но запись с таким номером в базе данных отсутствует.

## POST /posts: 201 Created

- Статус ответа (201 Created). Подтверждает, что операция не просто прошла успешно, а привела к появлению новой сущности в системе.
- Заголовок Location. Указывает прямую ссылку на созданный пост, например Location: /posts/101.
- Тело ответа (Body). Содержит JSON-представление нового объекта. 

## GET http://github.com: 301, Location: https://github.com/

- Браузер видит статус 301 и заголовок Location: [https://github.com/].
- Он не показывает пользователю ошибку или пустую страницу. Вместо этого он мгновенно формирует новый, второй запрос — уже по адресу [https://github.com/]
- Сервер перенаправляет с HTTP на HTTPS, чтобы защитить передаваемые данные с помощью шифрования и избежать дублей страниц в поиске.

## Общие вопросы 
- 401 означает что сервер меня не узнал,а 403 означает что узнал но доступ запрещен
 1) Пример работы  кода 401(Ответ сервера:
401 Unauthorized (или перенаправление на форму логина).):  GET https://github.com/settings/profile HTTP/1.1
Host: github.com
(Заголовок Authorization отсутствует, пользователь НЕ вошёл в систему)
2) Пример работы кода 403: GET https://myshop.com/admin/dashboard HTTP/1.1
Host: myshop.com
Cookie: session_id=pavel_logged_in_as_customer_123
(Сервер распознал пользователя: это Павел, обычный покупатель)

- Передача логина и пароля через query-параметры в URL несет несколько серьезных проблем безопасности:

1) Логи и история браузера: URL с параметрами сохраняется в истории браузера и может попасть в логи веб-сервера, прокси и других промежуточных систем, что увеличивает риск утечки учетных данных.

2) Кэширование: Некоторые браузеры и прокси могут кэшировать URL, включая параметры, что также повышает риск компрометации.

3) Отсутствие шифрования: Если соединение не защищено HTTPS, параметры URL передаются в открытом виде.

- Почему скрытие на фронтенде не защищает данные:

1) Прямые запросы к API. Злоумышленнику не нужен интерфейс сайта, чтобы отправить команду на сервер. Он может перехватить формат запроса и отправить его напрямую через терминал (например, с помощью curl) 
2) Изменение интерфейса в браузере. Если кнопка просто скрыта через стили (например, display: none) или условный рендеринг, пользователь может изменить код страницы прямо в инструментах разработчика браузера и сделать кнопку видимой.
